Audit of the "Pollet Grandglise" site (Hainaut, BE) started 2026-10-04. Gateway is a UniFi Cloud Gateway Max named DP-CGM-GRANDGLISE (MAC 6C:63:F8:29:69:37) running Protect on the console; the user sometimes calls it "the UDM". WAN is 4G only on a capped "hey! mobile S" SIM via a UniFi LTE router (user: "unifi ultra") with a legacy Huawei E3372 stick (192.168.8.1). No managed switch: cameras hang off unmanaged PoE switches. Four third-party XMeye/XiongMai ONVIF cameras on 192.168.1.x: bullets GRANDGLISE-B01 (00:DC:C3:52:E9:80), B02 (00:77:83:11:A5:8E), B03 "ENTREE" (00:91:C1:9F:D4:FC), and dual-lens PTZ P01 "ETANGE" (00:D5:B1:B4:FA:55, V33 firmware). Camera IPs drifted between docs and device info (.121 vs .43, .131 vs .252) — suspect DHCP, unverified. Symptom: only 3 of 4 cameras register in Protect. Site docs live in a BookStack at docs.cl6.us (book 5 "Pollet Grandglise"; API at /api, token auth; wiki pages are auto-generated from a controller sync pipeline, last sync 2026-07-31, so they may be stale). A dedicated SSH key ~/.ssh/id_ed25519_unifi_audit was created for console access; remove it from the console after the audit.

**Why:** the user runs a multi-site camera fleet documented in that wiki; knowing the site code, console model and camera vendor avoids re-deriving it each session.
**How to apply:** treat Protect cameras here as ONVIF third-party, not UniFi cameras; keep WAN data usage in mind for every recommendation (no scheduled speed tests, auto-updates, cloud backups without checking the cap). See [[pgl-network-dns]] for the WSL2 NAT caveat when reaching VPN sites.

Findings of the read-only pass on 2026-10-04 (report: ~/grandglise-audit-2026-10-04.md, nothing was changed): console LAN is 192.168.1.1, WAN 192.168.42.134 behind a UniFi Mobile Router Ultra "DP-UMR-GG" (UMR-Ultra-ROW, fw 1.17.11, Fast Ethernet ports) at 192.168.42.1, managed in UniFi Mobility, not adopted in the console. It does NOT reboot at random (I wrongly inferred that from paired link drops): outages follow three clock patterns — a reboot every Wednesday ~04:00, a ~10 s Ethernet link reset every 16 h after boot, and LTE stalls on many mornings (weekdays 07:02, weekends 09:02, ~6 min each). Signal is strong (RSRP -83, RSRQ -12, band 3). Plan limit 15 GB/month resetting on the 26th; phones on the UMR's own WiFi "CL6 Sec" use the SIM outside the gateway's counters. The "AI Port" at 192.168.1.2 is the Protect AI device, not a 4G device (wiki is wrong). Cameras now: ETANGE .131 (port 1), GARAGE_EST .122 (port 3), GARAGE_OUEST .123 (port 4), ENTREE .121 (offline). ENTREE has been physically failing since 2026-08-31 01:29: it boot-loops with a DHCP handshake every ~13 s for ~3 h after sunrise and is silent otherwise, so it needs an on-site power/cable/hardware check, not a settings change. Data: idle baseline ~90 MB/day, of which the daily IDS ruleset download is ~40 MB; each UniFi OS update is ~850 MB; Teleport VPN is a full tunnel relayed via TURN, so the user's whole laptop (including Claude Code API traffic) goes over the capped SIM while connected. Access notes: the UniFi API key works for the Network API and Protect integration API only (Protect internal API returns 401); Protect's database is readable on the console with `psql -h 127.0.0.1 -p 5433 -U postgres -d unifi-protect`; Protect logs are in /srv/unifi-protect/logs.

Applied on 2026-10-04 after the user's approval: IDS off, SNMP off, Network device auto-upgrade off, and two firewall policies ("Cameras - allow NTP" then "Cameras - block internet", matched on the four camera MACs). The user explicitly wants motion notifications, motion zones, retention (they set 7 days) and the onvif-recorder add-on left alone. ENTREE and ETANGE share an unmanaged gigabit PoE switch on gateway port 1; the garage cameras are wall-powered on ports 3 and 4. Twelve pages of the Grandglise wiki book were hand-updated; those pages are regenerated by the user's wiki pipeline, so durable notes belong in each site's "Drop Box" page above the `AUTO-CATALOGUE BELOW` marker. Later the same evening Smart Queues (a 2 Mb/s cap each way) was turned off at the user's request. UniFi OS and app auto-update were found to be already manual: the console logs "Startup: No auto-update scheduled", and the September OS updates were explicit admin requests (one from the user's own account), so my earlier claim that it auto-updates was wrong. Still open: UMR login for link drops, ENTREE on-site check, removing the audit SSH key and rotating the pasted keys. API techniques used are in [[unifi-api-access-notes]].

Verified later on 2026-10-04: the camera block drops live traffic (cameras retry 47.90.2.43:30019 constantly, nothing returns). The XMeye cameras do NOT use NTP: ONVIF GetSystemDateAndTime (works unauthenticated on port 8080) reports time source Manual and timezone ChinaStandardTime-8, yet clocks were within 1 s of true time, so something on the LAN sets them; the NTP allow rule had zero hits. Worth re-checking camera clock offsets on a later visit. The UMR's 16-hour event is an LTE re-attach with a new public IP followed by a double Ethernet link reset; the 20:02 occurrence was predicted and observed.
