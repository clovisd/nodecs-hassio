### Assistant — 2026-10-25 12:42 UTC

Yes. The beacon has three states, spinning, flashing and stopped, and the integration controls and reports all of them.

**Setting a state**

| You want | In an automation or script | From a dashboard |
|---|---|---|
| Spin | `blinkybeacon.spin` | Turn the light on (spin is the default), or pick the `spin` effect |
| Flash | `blinkybeacon.flash` | Pick the `flash` effect in the light's popup |
| Stop | `blinkybeacon.stop` | Turn the light off |
| Spin or flash for a set time | add `duration: 10` | — |

For example, to flash both beacons for 15 seconds:

```yaml
action: blinkybeacon.flash
data:
  device_id:
    - <home beacon device id>
    - <away beacon device id>
  duration: 15
```

You don't need to type device IDs. In the automation editor, the "Beacons" field is a device picker.

**Making button presses fast and reliable**

From what the panel exposes, these are the changes that would help most, roughly in order of impact.

*Speed (button press → pause on the server)*

- **The button's own delay is often the biggest one.** Many Zigbee buttons hold a single press back 300–500 ms to see whether it turns into a double press. A long press should fire when the hold starts, not on release. Triggering on the earliest event your buttons send can save more time than everything below put together.
- **The integration should send presses itself.** It would listen for the ZHA button event and post to the panel straight away, instead of an automation calling an action. That skips the automation engine and avoids a trap: an automation's default mode silently drops a second press while the first is still running. Automations would still get an event to hang the beacon off.
- **Presses reuse the open connection.** The 1 s read already keeps an HTTPS connection to the panel open, so a press on the same session skips the TLS handshake. A press goes out on its own, never queued behind a read, with short timeouts.
- **The panel is read again right after a press,** so Home Assistant shows the pause one round trip later instead of waiting for the next poll.

*Reliability*

- **No blind retries.** A press that timed out may already have paused the match, and resending it could burn a second timeout. The integration would resend only when the request provably never left. Otherwise it checks the panel's press log first and resends only if the press isn't there.
- **Duplicates are dropped.** Zigbee can deliver the same frame twice. A repeat from the same button within about half a second is ignored.
- **Every press reports its outcome.** The panel logs each press as executed, test, error or none, with a detail. The integration would read that back and show it with the round-trip time, so a failed press is visible at once (for example a notification or a red beacon).
- **The button key is its own credential.** It's separate from the admin login, never logged, and a refusal asks for it again.
- **Button health needs more than ZHA's "available".** Battery buttons often check in only hourly, so a dead button can look available for a long time. It's worth showing last-seen time, signal and battery, the panel's button-outage records, and a test press before each match. Presses before a match goes live are logged as "test" only, so they never pause anything.
